# 検索・更新・整理・共有（v0.9.0）

## RSSの条件付き取得

`PodcastHttp` は200応答を最後まで解析し、`PodcastRepository` が内容とETag・Last-Modified・最終応答URLを同じDBトランザクションで保存する。次回は保存した応答URLと完全に一致するリクエストにだけ検証ヘッダーを送る。転送先が別のリソースへ変わったときに検証情報を流用しない。

304応答では解析・エピソードの保存・新着通知を省き、既存の履歴やキューを保持する。失敗・壊れたXMLでは最後に成功した検証情報を維持し、200応答に検証ヘッダーがなければ古い情報を消す。検証情報のない304は受け入れない。サーバーが未対応の場合は通常取得する。

同じ番組の更新は直列化し、全体の通信は最大3接続。最後の確認・成功時刻とエラーを端末内に保存する。管理画面の個別再取得も同じ処理を使う。

## 登録済みエピソードの検索

エピソード画面の検索アイコンから、タイトル・説明の部分一致で検索する。空白で区切った語はすべてを含む回を探す。絞り込み（未再生・保存・お気に入り・履歴）もDB上で適用する。

一覧用の最新1,000件や説明512文字のプレビューに限定せず、保存済みの全文をSQLite内で検索する。結果は150件ずつ。入力は300ms待って処理し、古い検索結果が後から画面を上書きしないようにする。画面を離れたら検索を停止し、元の一覧と検索結果のスクロール状態を分けて保持する。検索で見つけた古い回を再生した場合も、検索を閉じた後に現在の回を取得できるようにする。

## 操作の取り消しとキューの並べ替え

手動の再生済み／未再生への変更と、キューから外す操作は10秒間取り消せる。通知の「元に戻す」から実行する。最後の操作が対象で、時間切れ・アプリのプロセス終了では破棄する。

再生状態と、所属していた全キューの前後の要素を記録する。取り消しでは、その後に追加・並べ替えられた他の要素を保持しながら元の位置へ挿入する。実際の再生で進捗や履歴が変わった場合は上書きしない。削除済みのキューや再生完了済みの回を復活させない。音声の自動削除が対象となる実再生の完了は取り消し対象ではない。

キューの右端のハンドルをドラッグして並べ替える。端では自動スクロールし、離したときに1エピソードの位置だけを保存する。戻る・ジェスチャーキャンセルではプレビューを破棄する。長押しメニューの「上へ移動」「下へ移動」も残し、再生画面が前面にある間は背後のキューの戻る処理を無効にする。

## ストレージと更新

設定の「ストレージと更新」に音声・画像キャッシュ・利用可能容量を表示する。画像はCoilのキャッシュサイズ、音声は実ファイル、空き容量は保存先ファイルシステムのStatFsから取得する（領域の確保はDownloadManagerが担当）。

- 保存タブ: 保存済み・取得中・失敗・Wi-Fiやネットワーク待ちを確認し、再試行・削除できる。
- 更新タブ: 全番組の最終確認、失敗内容、前回成功を確認し、番組ごとに再取得できる。
- 再生済みの保存音声と画像キャッシュは、確認した上でまとめて削除できる。再生中の保存音声を削除しても、再生位置・キュー・明示したチャプター位置の扱いを保って配信元へ切り替える。

詳細の読み込みとサイズの計算は画面表示中に行う。通常の一覧に管理用の説明やエラーを常設しない。

## 共有・コピー

エピソードの詳細・再生画面の共有ボタン、一覧の長押し「共有・コピー」から利用する。番組の共有は「購読元」から行う。

RSSのitem/link、Atomのalternate link、HTTP(S)のpermalink GUIDを保存する。共有先にはエピソードのWeb URLを優先し、なければ音声URLを使う。タイトル・リンク・共有本文をコピーでき、Androidの標準共有画面から他アプリへ渡せる。

共有の情報は起点の行が消えたり次の回へ進んだりしても保持する。現在選択されているエピソードでは「再生位置を含める」を選べる。本文に `1:01（61秒）` のように追記し、共有画面を開いた瞬間の位置を使う。別の回の位置を混ぜず、Webサイトが対応しているか不明なシーク用パラメーターを勝手にURLへ付けない。

## 保存形式と検証

schema 5でエピソードURLと更新情報を追加する。schema 1〜4の固定SQLから移行し、購読・キュー・進捗・音声参照・お気に入り・履歴・チャプターを保持する。

実HTTPの200→304→失敗→ヘッダーなし200→壊れたXML→成功、転送時の検証情報、DB再開後の取得、説明末尾の検索、複数キューの取り消しと競合、実ViewModel経由の検索・ドラッグ、共有Intentとクリップボード、管理画面の再試行を検証する。

以前提供されたOPMLとキャッシュ済みRSSでも、123番組・36,486エピソードの登録と全番組更新が256MiBのテストヒープ内で完了した（観測ピーク201MiB）。一覧外の回の全文検索はこの環境で約505ms。入力データと専用診断テストはリポジトリに含めない。

最終確認: 通常の135テストと画面撮影用の4テスト（計139件）、`lintDebug`、`assembleDebug`が成功。全画面のライト／ダーク表示、文字拡大、新機能の画面もRobolectricで撮影した。実機での確認は未実施。
